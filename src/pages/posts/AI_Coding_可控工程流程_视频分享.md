> **一句话结论**<br>这场 workshop 的重点不是找到一个神奇 prompt，而是为一个会受上下文影响、会遗忘、却能高速产出的执行者设计控制系统：先对齐，再外部化，再切片执行，最后用独立审查和反馈闭环收回质量责任。

## 执行摘要

Matt Pocock 的判断很直接：AI 确实改变了编码方式，但它没有取消软件工程的约束。相反，需求澄清、任务切分、模块边界、反馈循环与代码审查，在 Agent 参与后更重要，因为实现速度增长得远快于人类理解和验收能力。

视频展示的是一条从模糊需求走向交付的控制闭环。人类在前段负责业务判断、取舍和验收标准；Agent 在中段承担探索和实现；新上下文的审查、自动化验证与人工 QA 则在后段收回风险。AI 加速的是实现，而不是免除工程责任。

> **阅读提示**<br>文中“视频中”指讲者在这场 workshop 的演示或主张；“落地建议”是基于视频提炼的团队实践，不应与视频原话混同。Smart zone / dumb zone 等概念应视为经验性工作模型，而非跨模型、跨任务的硬阈值。

## 1. 先接受两个现实：模型会受上下文影响，也会“失忆”

### 1.1 Smart zone / dumb zone：别让一个会话无限变长

视频借用 HumanLayer 的经验框架说明：会话刚开始时，模型更容易聚焦；随着上下文不断堆积，它更容易遗漏约束、执着于局部路径或做出低质量决定。Pocock 把相对可靠的状态称为 smart zone，把退化后的状态称为 dumb zone。

他把大约 100K tokens 作为自己的警惕线，但这不是普适定律。不同模型、任务复杂度、仓库规模和上下文构成都会改变阈值。真正可迁移的原则是：任务要足够小，主会话要保留余量，审查者不要继承实现会话的上下文疲劳。

> **由此推导的工作原则**<br>把长任务拆为能在清晰上下文内完成的单元；把长期状态写到仓库工件中；需要审查时，优先另开 fresh context，而不是让刚写完代码的同一会话自审。

### 1.2 Memento 类比：把可靠状态放到会话外

Pocock 把 LLM 的会话比作《记忆碎片》主角：一次 session 经历系统提示、探索、实现和测试，清空后就回到起点。他个人更偏好 clear，而不是不断 compact 历史，因为压缩摘要可能把旧误解沉积到下一轮判断中。

重点并不是“永远不要 compact”，而是流程应能在 fresh context 下恢复。PRD、ADR、任务卡、验收证据等因此不是文档仪式，而是项目对 Agent 的外部记忆；它们让新会话或新 Agent 能接住正确的状态。

### 把两条约束变成控制策略

| **常见失控点** | **为什么会失控** | **对应控制** |
| --- | --- | --- |
| 同一会话一直延长 | 上下文噪音增加，关键约束被淹没 | 小任务、清空上下文、fresh-context review |
| 只靠聊天记录续接 | 状态不可验证，摘要可能携带旧误解 | PRD、决策记录、带验收条件的任务卡 |
| 一次生成大功能 | 反馈出现得太晚，偏差被大量代码放大 | vertical slice / tracer bullet，尽早跑通端到端 |

## 2. 不先写代码：先让人和 Agent 形成共同设计概念

### 2.1 Grill Me：让 AI 采访人类，而非替人猜业务

视频中，Pocock 从一个“留存下降，加入 gamification”的模糊 brief 开始。他先清空上下文，再运行 Grill Me。这个 skill 的目标不是立即产出计划，而是沿着决策树逐支追问：积分来自哪里？哪些行为会被刷分？历史行为是否回填？成长曲线如何设计？什么明确不做？

关键的人机分工是：AI 一次只问一个问题、给出建议选项并暴露缺口；人类提供领域知识、做价值取舍、确认边界。输出不是代码，而是 shared design concept——一套双方真正理解的设计判断。

> **容易忽略的细节**<br>这一步不必由开发者独自完成。涉及业务规则时，领域专家、开发者和 Agent 可以共同参与；代码库探索也可以交给隔离的子 Agent，再只把结论带回主会话，以节省主上下文。

### 2.2 PRD 是目的地文档，不是“规格编译器”

在 Grill Me 之后，前述对话已经积累了高价值上下文。视频随后把它沉淀为 PRD：问题、目标用户、方案、用户故事、关键实现与测试决策、范围外事项都被写入其中。PRD 的主要作用是外部化共同理解，给后续 fresh context 一个可靠的接力点。

Pocock 说，在已经充分对齐的低风险场景中，他不会逐字审 PRD，因为那往往只是再次审模型的摘要能力。这是个人工作法，不是免审规则。权限、支付、数据迁移、安全、合规和不可逆操作仍应由人明确审查。

### 2.3 从 PRD 到 Kanban / DAG：任务要小，也要能产生真实反馈

Pocock 不满足于线性的 phase 1、phase 2、phase 3 计划，因为它们不善于表达阻塞关系，也不方便安全并行。他把 PRD 变成 Kanban：每个 ticket 说明依赖、可否 AFK、验收方式；未被阻塞的任务组成可并发执行的 DAG。

| **水平切分的惯性** | **垂直切片 / tracer bullet** | **为什么更适合 Agent** |
| --- | --- | --- |
| 先建完数据库，再 API，最后 UI | 一个最小任务贯穿数据、服务、界面与验证 | 尽早得到端到端、可见、可测试的反馈 |
| 系统直到最后才可演示 | 第一片就能验证真实用户路径 | 偏差在少量代码时被发现和纠正 |
| 任务很小但没有产品信号 | 任务既小到留在 smart zone，又完整到能验收 | Agent 的下一步有更可靠的证据可依 |

## 3. 实现可以 AFK，交付绝不能无人负责

### 3.1 先可观察，再自动运行

视频将规划称为人类“日班”，将实现称为 Agent“夜班”。但在把任务交给后台循环前，Pocock 先做 human-in-the-loop 试跑：观察 Agent 如何读仓库、选择 issue、修改代码、运行验证，并据此调整任务描述、prompt 和环境。只有当这条循环已经可观察、可调校，才适合 AFK。

后段演示的 Sandcastle 使用 worktree、隔离分支和 sandbox 来并行处理可执行的任务；它是吞吐量扩展器，不是工作流的前提。没有清晰依赖、隔离边界和验证条件时，并发 Agent 只会更快制造冲突。

### 3.2 AI review 可以有，但要与实现者隔离

视频对 review 的态度很务实：AI 写得越多，人类 review 的压力不会凭空消失。Agent 可以参与自动审查，但不宜让已经耗尽上下文的实现 Agent 审自己的代码；更好的选择是让一个 fresh context 的 reviewer 从相对干净的状态重新检查。

人工 QA、代码审查与团队评审仍是交付门槛。实现吞吐量必须受 review 和验收能力约束；否则团队只是更快地积累看不懂、验不完的变更。

### 3.3 反馈循环才是 Agent 的导航系统

Pocock 的关键判断是：没有反馈循环，Agent 就是在 blind coding。测试、类型检查、构建、运行时验证和端到端路径不是收尾动作，而是让 Agent 在每个小循环里自我纠偏的依据。视频中也特别指出，前端与视觉质量的自动化信号更弱，因此更需要短验证闭环和人工 QA。

**可执行的最低验证集：** 每张任务卡至少说明验收命令、测试范围和禁止改动范围；有 UI 的任务还应补充可视化或 E2E 验收。TDD 在这里的价值是提供更紧、更可信的反馈，而不是自动保证正确。

### 3.4 规则应放在正确的上下文里

视频还给出一个细节：实现 Agent 的规则可按需 pull——需要时再读取对应 skill，避免起始上下文过重；reviewer 的标准则应明确 push 到它的上下文，因为审查工作的任务就是按这些标准检查。把所有规则塞进每个 Agent 的开场提示，反而可能让它一开始就处于噪音过高的状态。

## 4. AI 时代的架构目标：缩小人类必须理解的表面积

视频后段借用 John Ousterhout 的 deep modules 概念。大量细碎、相互牵连的 shallow modules 会让人和 Agent 都难以理解依赖图，也容易诱发“每个小函数一层测试”的低价值测试堆积。

更合适的方向不是机械合并文件，而是设计小而稳定的公开接口，将更多实现复杂度封装在模块内部。人类重点把握接口形状、行为和边界；Agent 可以更多承担内部实现。这让 review 更接近验证模块契约，而非逐行追踪每个碎片。

| **浅模块（应避免的风险）** | **深模块（应追求的性质）** |
| --- | --- |
| 大量细小文件和复杂依赖，理解路径长 | 公开接口小而清晰，内部可以承担较多复杂性 |
| 测试围绕碎片，难证明系统行为 | 测试围绕模块契约和真实用户路径 |
| AI 与人都需要频繁跨文件拼接语义 | 调用者只需理解稳定边界，review 表面积更小 |

## 5. 从视频提炼的团队试点方案

> **以下为落地建议，而非视频规定动作**<br>建议不要一上来做全项目自动驾驶。先选一个低风险、可在一周内完成、能形成真实 vertical slice 的需求，用可测量的方式验证这条闭环是否降低返工与审查成本。

| **阶段** | **要做什么** | **完成信号** |
| --- | --- | --- |
| 选题 | 选择低风险、边界清晰、可端到端验证的一条用户路径 | 能写出目标、非目标、数据/权限影响和验收方式 |
| 对齐 | 让 Agent 连续追问业务规则、边界条件、异常与取舍 | 形成共享设计概念；高风险事项有人明确确认 |
| 编排 | PRD 转为带依赖的 vertical-slice tickets | 每张卡都有输入、输出、验收命令和禁止改动范围 |
| 试跑 | 用 HITL 完整观察一张卡的实现、测试与审查 | 能定位并修正任务模板、prompt 或环境缺口 |
| 放量 | 仅对无依赖、隔离充分的任务开放 AFK / 并行 | review、QA 与回滚容量仍覆盖实际产出 |
| 复盘 | 记录首轮通过率、返工原因、review 时长和缺陷逃逸 | 下一轮只优先修一个最弱环节 |

**治理边界：** 密钥、生产数据、外部写操作、依赖安装、数据迁移和权限变更都应有明确授权与审查。不要把“能跑 AFK”误解为“可以跳过控制面”。

## 6. 不要误读这场 workshop

**不是“换一个万能 prompt”。** 核心是对齐、状态、反馈和审查的系统设计。

**不是“PRD 越长越好”。** PRD 的价值在于保存长期语义和关键决策；临时 issue 文档若不清理或标注过期，反而会形成 doc rot，并误导未来的 Agent。

**不是“更多 Agent 一定更快”。** 并发只会放大任务拆分、依赖建模和共享边界的质量。

**不是“约 100K tokens 是硬红线”。** 这是讲者的经验性警惕线。团队应观察自身模型、仓库和任务，建立合适的任务粒度与上下文预算。

**不是“自动测试代替人工 QA”。** 测试能提升可验证性，却不能自动覆盖体验、可访问性、性能、业务语义和组织风险。

## 结语

这场视频最值得带走的，不是 Grill Me、Kanban、Ralph 或 Sandcastle 中的任何一个名词，而是一种工程判断：当执行者会遗忘、会受上下文影响、又能高速产出时，团队必须把对齐、状态、反馈和审查设计成系统。

**成熟的 AI Coding 不应以“Agent 能独自跑多久”来衡量，而应以“换一个全新的 Agent 后，团队能否仍靠清晰工件、可靠反馈与有限审查成本，持续交付正确变更”来衡量。**
