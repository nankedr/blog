> **一句话结论**<br>
> 这五个 Skill 不是五段“神奇提示词”，而是一条工程控制链：先通过追问形成共同理解，再把目的地写成 PRD，把旅程拆成有依赖的垂直切片，用 TDD 提供执行反馈，最后持续改善代码库边界，让下一轮 Agent 更容易做对。

## 执行摘要

Pocock 的出发点是：开发者现在可以随时调度一批能力中等到良好的 AI 工程师，但它们缺少稳定的长期记忆，也不会自然继承过去项目中的隐性经验。因此，AI Coding 的关键不只是选择更强的模型，而是把团队已有的工程方法变成明确、可重复的过程。

他把这些过程写成 Skills，让 Agent 每次都沿着相对固定的路径工作。视频展示的五个 Skill 覆盖了需求澄清、规格沉淀、任务拆分、实现反馈和架构治理，组合起来形成一条完整链路：

`模糊想法 → /grill-me → /write-a-prd → /prd-to-issues → 执行 Agent + /tdd`

代码库的长期维护则形成另一条回路：

`/improve-codebase-architecture → 重构 RFC → /prd-to-issues → /tdd 实施`

### 五个 Skill 的分工

| Skill | 要解决的问题 | 主要产物 | 人类需要把关的内容 |
| --- | --- | --- | --- |
| `/grill-me` | 双方是否真的理解了同一个需求 | 共享设计概念、已确认的决策树 | 业务选择、范围、取舍 |
| `/write-a-prd` | 如何把高价值对话保存下来 | 作为父任务的 PRD / GitHub Issue | 用户故事、目标与非目标 |
| `/prd-to-issues` | 如何从目的地走到交付 | 有阻塞关系的垂直切片任务 | 切片顺序、依赖和验收边界 |
| `/tdd` | 如何让执行过程持续获得反馈 | 测试保护下的实现 | 接口变化、需验证的行为 |
| `/improve-codebase-architecture` | 如何降低代码库对人和 Agent 的理解成本 | 架构候选方案、重构 RFC | 模块边界、设计品味和风险 |

> **版本提示**<br>
> 视频使用 `/write-a-prd`、`/prd-to-issues` 等名称；配套文章和持续演化中的仓库后来出现了 `/to-prd`、`/to-issues`、`/to-spec`、`/to-tickets` 等命名。本文按视频当时的名称总结，不把当前仓库状态倒推回视频。

## 1. `/grill-me`：先形成共同理解，不要急着生成计划

这个 Skill 只有三句话，核心约束可概括为三点：

1. 持续采访用户，直到双方对方案形成共同理解。
2. 沿设计决策树逐个分支推进，并先解决前置决策。
3. 如果答案可以从代码库中得到，就直接探索代码，而不是把问题甩给用户。

### 为什么需要“设计树”

Pocock 借用 Frederick P. Brooks Jr. 在《The Design of Design: Essays from a Computer Scientist》中讨论的设计树视角：一个看似简单的功能，往往会在每次选择后继续分叉。例如搜索页先要选择普通文本框还是高级搜索；如果选择高级搜索，又要继续决定过滤项、排序方式和交互规则。没有走完关键分支就开始编码，后续返工几乎是必然的。讲者也特意保留了出处边界：他不确定概念是否源自这本书，只是自己第一次在那里读到。

这个 Skill 的价值是抑制 Agent 过早收敛。Pocock 观察到，Claude Code 在计划模式中很容易很快给出一份计划或文档，但“已经生成计划”不等于“已经理解需求”。`/grill-me` 强制对话继续发生，直到重要分支被显式处理。

### 视频中的实际案例

他向 Claude 提供了一份 Markdown 研究材料，希望给课程视频编辑器增加文档编辑能力。Agent 先探索相关代码，再连续追问：文档存放在哪里、UI 如何布局、哪些模式显示文档面板、文档生命周期是什么、工具接口应该长什么样等。

这次相对较短的对话也问了 16 个问题。对于复杂功能，他会花 30～45 分钟回答 30、40 甚至 50 个问题。

### 最重要的启示

- Skill 的价值不由长度决定。短 Skill 只要在正确时机改变 Agent 的行为，就可能非常有用。
- 需求澄清不是让 Agent 猜得更完整，而是让人负责业务判断，让 Agent 负责系统性暴露缺口。
- 能从仓库验证的事实应由 Agent 自己查，用户只回答必须由领域知识或偏好决定的问题。

## 2. `/write-a-prd`：把共同理解变成“目的地文档”

当讨论已经充分、并且确定要实施时，Pocock 才进入 PRD 阶段。这个 Skill 允许跳过已经完成的步骤：如果刚做完深度访谈，就不必机械地再问一遍。

视频中的流程大致是：

1. 获取用户对需求的详细描述。
2. 探索仓库，验证描述中的事实和技术假设。
3. 对尚未对齐的部分继续深挖。
4. 勾勒需要新建或修改的主要模块。
5. 按模板生成 PRD，并提交为 GitHub Issue。

### PRD 应重点保存什么

Pocock 特别强调用户故事。用户故事用自然语言描述系统期望呈现的行为，是业务意图与后续实现之间的桥梁。他也坦言，自己还没有找到唯一正确的用户故事格式；团队完全可以采用更熟悉的形式，例如结构化的 Given / When / Then。

视频案例的 PRD 描述了一个较大的文章编辑功能：现有页面每次 AI 交互都会重新生成整篇文档，目标是增加左右分栏体验，左侧保留对话，右侧成为可编辑文档面板。PRD 保存问题、目标体验、用户故事以及少量关键实现判断。

### “目的地”与“旅程”的区别

PRD 负责说明最终要得到什么，但不负责逐步说明如何抵达。实现细节也不宜写得过死，否则代码演化后，PRD 很快变成过期快照，反而会误导未来的 Agent。

因此，一个较耐用的 PRD 应优先保存：

- 问题和目标，而不是当前文件结构的复述；
- 可观察的用户行为，而不是逐函数实现指令；
- 已确认的关键边界与取舍；
- 少量会影响整体设计的实现决策。

## 3. `/prd-to-issues`：把目的地拆成可执行的旅程

第三个 Skill 把父 PRD 转成可独立领取的任务，并建立任务之间的阻塞关系。它不是简单地把大文档按章节切碎，而是要求优先设计垂直切片。

### 为什么是垂直切片

Pocock 的拆分原则是尽早暴露“未知的未知”。如果方案依赖一个新服务，或者要首次连接两个过去没有集成过的系统，那么最先做的任务应尽快贯穿这条路径，验证整体方向是否可行。

这里采用的是 tracer bullet（曳光弹）式的垂直切片：每个 Issue 是一个穿过必要集成层的薄切片，而不是“先做完数据库、再做完 API、最后做完 UI”的水平分层。两者侧重点略有不同——vertical slice 强调端到端交付一小段行为，tracer bullet 更强调用可运行细路径验证架构和集成——但都能更早带来真实反馈，并在方向错误时控制沉没成本。

### 任务不仅要小，还要表达依赖

视频中的复杂 PRD 最终只拆成四个切片。第一个切片先验证文档编辑引擎；如果核心引擎不可行，后续方案就需要尽早调整。第二个任务没有前置阻塞，因此可以与第一个并行；第三个被第一个阻塞；第四个 Monaco 编辑器切换功能则被第二个阻塞。

这种依赖图有两个作用：

- 并行 Agent 只领取真正无阻塞的任务，降低冲突和返工；
- 后续发现 QA 问题时，可以把新任务接回现有依赖图，而不是维护一份容易失真的线性计划。

每个子 Issue 会引用父 PRD 和对应用户故事。视频中，执行该任务的 Claude 最终提交了一个纯函数文档编辑引擎，并用 28 个测试覆盖验收条件；完成后它评论并关闭 Issue，使下游任务解除阻塞。Pocock 使用 Ralph loop 自动循环领取和执行这些任务，但视频只把它作为执行器带过；它不是这五个 Skill 之一，也不是 TDD 本身。真正决定自动化能否可靠运行的，仍是前面的任务质量和反馈条件。

## 4. `/tdd`：用红—绿—重构给 Agent 持续反馈

在五个 Skill 中，`/tdd` 的内容明显更长，包含测试哲学、重构、Mock 和深模块等指导。Pocock 认为，高质量 TDD 是他最稳定地提升 Agent 输出质量的方法。

### 先谈接口，再写测试

这个 Skill 的第一步不是立刻生成测试，而是先与用户确认需要改变哪些接口、哪些行为必须被验证，并围绕可测试性设计边界。

原因是接口变化属于高影响决策。一个由大量细小、相似模块组成的代码库，会迫使 Agent 在许多文件之间推断职责和依赖；如果模块内部可以复杂，但公开接口小而清晰，那么 Agent 更容易理解调用方式，测试也可以集中在模块边界。这里的“深模块”是指用简单接口隐藏较多复杂度，不等于盲目制造大文件或巨型类。

### 执行循环

`/tdd` 要求一次只推进一个行为：

1. 写一个失败测试，确认它因预期原因失败。
2. 写最少的实现使测试通过。
3. 继续下一个行为。
4. 完成后寻找可重构之处。

对 Agent 而言，测试不只是交付前检查，而是每一步的导航信号。它缩短了“生成代码—得到反馈—修正方向”的周期。

### 视频明确承认的局限

Pocock 认为重构阶段目前并不总是理想。LLM 往往不愿大幅修改自己刚刚写完、仍留在当前上下文中的代码；清空上下文或让新的 Agent 审视实现后，它反而可能更容易发现结构问题。

这说明 TDD 并不会自动解决架构问题。它依赖清晰的测试边界，而测试边界又依赖合理的代码结构。

## 5. `/improve-codebase-architecture`：让代码库本身更适合 Agent

第五个 Skill 把注意力从单次功能转向长期环境。Pocock 的判断很直接：糟糕的代码结构会持续降低 Agent 的输出上限；AI 可以加速写代码，也会加速软件熵的累积。

### 第一步：像 Agent 一样自然探索

这个 Skill 先让 Agent 正常浏览代码，并记录理解过程中的摩擦，而不是预设一个重构答案。它重点寻找三类信号：

- 理解一个概念需要在许多小文件之间反复跳转；
- 为了可测试性抽出了很多纯函数，但真实缺陷藏在调用和组合处；
- 高耦合模块把集成风险集中在边界缝隙中。

这些信号会被整理成一组“模块深化”候选项，即把浅模块改造成公开接口更小、内部能力更强的深模块。

### 第二步：并行设计多个接口，而不是只修补现状

用户选定一个候选项后，Skill 会让三个并行子 Agent 分别给出差异足够大的接口方案；面对大型重构，Pocock 也用过五个方案。主 Agent 再比较这些设计，给出推荐理由，并在必要时组合成混合方案。

这一步的意义不是用投票替代设计，而是扩大方案空间，避免第一种可行答案成为默认答案。最终仍需要人类凭借业务背景、演化成本和设计品味做选择。

### 第三步：把选择写成 RFC，再走正常交付链路

选定方案后，Skill 创建一个 GitHub Issue 形式的重构 RFC。这个 RFC 仍然只是目的地，随后再交给 `/prd-to-issues` 拆分旅程，并通过 `/tdd` 实施。

Pocock 建议周期性运行这类检查，例如每周一次，或在一轮高强度功能开发之后。但一次只处理一个重要候选项，因为架构决策认知负担高，也需要持续的人类参与。

## 6. 五个 Skill 背后的统一方法

把五段内容放在一起，可以看到它们不是独立技巧，而是同一套工程观的不同控制点。

### 6.1 把隐性经验外部化

Agent 没有稳定记忆，因此“团队通常怎么做”不能只存在于某个资深工程师脑中。Skill、PRD、Issue、测试和 RFC 共同构成项目的外部记忆。

### 6.2 把不同类型的决策分开

- `/grill-me` 解决“我们是否理解同一件事”；
- PRD 解决“最终要达到什么状态”；
- Issues 解决“以什么顺序走过去”；
- TDD 解决“每一步如何获得可信反馈”；
- 架构 Skill 解决“如何降低下一轮工作的理解成本”。

把这些问题混在一个超长提示里，容易让需求、计划、实现和审查同时漂移。

### 6.3 优先验证风险，而不是优先完成层次

垂直切片、接口先行和测试先行都在做同一件事：尽早把最大不确定性变成可观察结果。Agent 的速度越快，越需要缩短反馈回路，否则它只会更快地扩大偏差。

### 6.4 人类责任并没有消失

视频中的人类关口很明确：人决定业务取舍、确认接口变化、选择测试行为、挑选架构候选并判断设计方案。Agent 擅长探索、列举、执行和循环验证，但最终的价值判断与风险责任仍在人。

## 7. 适合团队试点的最小版本

> 以下是基于视频提炼的落地建议，不是讲者给出的固定模板。

不要一开始就复制整套自动化。可以选一个低风险、可在数天内完成的真实功能，先跑通下面的最小闭环：

| 阶段 | 最小动作 | 完成信号 |
| --- | --- | --- |
| 对齐 | 用追问列清目标、非目标、关键分支和异常路径 | 重要问题不再依赖 Agent 猜测 |
| PRD | 保存问题、用户故事、边界和关键决策 | 新 Agent 只读 PRD 也能说清目的地 |
| 切片 | 先做最能验证风险的端到端薄切片 | 每张任务卡都能独立验收，并标明依赖 |
| 实现 | 对预先确认的行为执行红—绿循环 | 每次改动都有可运行的反馈 |
| 审查 | 用 fresh context 检查实现与规格 | 审查者不继承实现者的路径依赖 |
| 复盘 | 记录返工原因、首轮通过率和架构摩擦 | 下一轮只优先修复最弱的控制点 |

### 一张任务卡至少应包含

```text
父 PRD：
目标 / 对应用户故事：
本任务贯穿的垂直切片：
前置依赖与会阻塞的任务：
允许改变的接口：
验收行为与验证命令：
明确不做什么：
```

## 8. 不要误读这段视频

**不是 Skill 越长越好。** `/grill-me` 的例子恰好说明，短而准确的流程约束也能显著改变行为。

**不是写完 PRD 就可以无人值守。** PRD 只描述目的地；切片、依赖、权限、反馈和审查共同决定自动执行是否安全。

**不是任务越小越好。** 只按文件或技术层拆出的微任务，可能很小却无法独立验证。好的切片既要小，也要产生端到端反馈。

**不是测试越多越好。** 视频强调的是围绕行为和模块边界建立反馈，不是为每个内部函数堆测试。

**不是并行 Agent 天然更快。** 只有依赖关系清楚、工作边界可隔离时，并行才不会把冲突和返工一起放大。

**不是 Agent 可以独立决定架构。** 多方案设计扩大了选择空间，但最终方案仍需要人类品味和项目背景。

**也不只适用于 Claude Code。** 视频的命令名和演示环境来自 Claude Code、GitHub Issues 与 Ralph loop，但“澄清—外部化—切片—反馈—治理”的方法可以迁移到其他编码 Agent。

## 结语

这段视频最值得带走的，不是五个命令名，而是一个判断：当代码生成变得便宜，真正稀缺的能力会转向需求对齐、任务设计、反馈质量和架构判断。

Skill 的作用，是把这些原本依赖个人经验的工程动作，压缩成 Agent 能重复执行的路径。成熟的 AI Coding 工作流也不应只问“Agent 一次能写多少代码”，而应问：它是否理解了正确的问题，是否优先验证了最大风险，是否能用反馈修正自己，以及这次交付有没有让下一次工作更容易。
