> 不是一次性生成一份“完美计划”，而是用地图、决策票、依赖关系和多种验证会话，逐步清除通往目标的迷雾

> **一句话结论**<br>
> Wayfinder 不是替你预先猜完所有实现步骤，而是把“一次 Agent 会话装不下、路径又不清楚”的工作放进 Issue Tracker：先定义目的地，再把当前能说清的问题建成有依赖的决策票，将暂时说不清的部分保留为迷雾；研究、原型、追问或现实任务每解决一个问题，地图就更新一次，直到信息足以沉淀规格并进入正常实现流程。

## 执行摘要

Pocock 认为，自己此前使用或创建的规划工具都过度绑定单一会话。为了不挤出 Agent 上下文窗口中质量更高的“smart zone”，开发者往往会提前把雄心勃勃的项目人为缩小；但真正开始追问后，又常遇到当前会话无法回答的问题、需要额外研究的事实，或必须先做出来才能判断的交互。这使“切小任务”变成了适配 AI 限制，而不是服务项目本身。[00:00](https://www.youtube.com/watch?v=F3lL98Pj90o&t=0s) [00:56](https://www.youtube.com/watch?v=F3lL98Pj90o&t=56s)

Wayfinder 的解法是把**规划本身也拆成跨会话工作**。它用一张共享地图记录目的地、已经做出的决定、当前可领取的决策票，以及仍无法精确表述的“战争迷雾”。每张票在独立 Agent 会话中处理，类型可以是研究、原型、追问或任务；票与票之间用阻塞关系表达“哪些决定必须先发生”。因此，地图不是静态甘特图，而是一个随证据和决定不断扩张、收缩和重排的决策网络。[02:10](https://www.youtube.com/watch?v=F3lL98Pj90o&t=130s) [03:34](https://www.youtube.com/watch?v=F3lL98Pj90o&t=214s)

视频展示的完整工程链路是：

```text
模糊而庞大的想法
    ↓
/wayfinder：定义目的地、建立地图、逐张解决决策票
    ↓
决策充分，迷雾清除
    ↓
/to-spec：把地图压缩为可构建规格
    ↓
/to-tickets：拆成实现票
    ↓
逐票实现 → code review
```

这里有两个必须分开的阶段：Wayfinder 中的是**决策票**，用来回答“做什么、为什么、边界是什么、还需验证什么”；规格之后的是**实现票**，才负责把已经理解的方案构建出来。[09:44](https://www.youtube.com/watch?v=F3lL98Pj90o&t=584s) [13:14](https://www.youtube.com/watch?v=F3lL98Pj90o&t=794s)

## 1. 背景：单会话规划为何限制了项目规模

Pocock 此前常用 `/grill-me` 或 `/grill-with-docs`，让 Agent 通过持续采访把模糊需求问清楚。他仍然认为深度追问是重要的基础能力，但它天然围绕当前会话展开。若工作规模超过一个上下文窗口，尤其超过讲者所说的“smart zone”，会话就不得不同时承载仓库探索、问题回答、研究材料、原型反馈和最终文档，信息压力很快累积。[00:56](https://www.youtube.com/watch?v=F3lL98Pj90o&t=56s)

常见应对方式是人类先把项目切成一小块，只让 Agent 规划眼前部分。问题在于，真实的大型工作并不会沿一条已知直线推进：

- 追问到一半，可能出现一个暂时回答不了的问题；
- 某个技术选择需要先查文档、API 或现有代码；
- 某个界面或状态模型必须先做原型，讨论才有足够高的清晰度；
- 某个决定要等权限、现场勘测、账号开通或其他现实任务完成；
- 不同决定存在先后依赖，有些又可以并行验证。

因此，难点不是“让单次计划写得更长”，而是给规划建立跨会话的持久状态、任务类型和反馈循环。Wayfinder 保留了 grilling，但把它从唯一规划容器降为地图上的一种决策手段。[01:18](https://www.youtube.com/watch?v=F3lL98Pj90o&t=78s) [02:37](https://www.youtube.com/watch?v=F3lL98Pj90o&t=157s)

## 2. 核心心智模型：起点、目的地、地图、迷雾与前沿

### 2.1 先承认路线未知

大型工作通常有一个起点，也能模糊描述希望到达的状态，但两者之间的路径并不清楚。Pocock 把这类状态画成一张地图：起点在一端、目的地在另一端，中间覆盖着 fog of war。第一次 grilling 只能建立基本方向；若一次对话已经足够清晰，就不需要 Wayfinder。若仍有大量未知，则应继续开研究、原型或追问会话，而不是假装已经拥有完整计划。[02:10](https://www.youtube.com/watch?v=F3lL98Pj90o&t=130s)

### 2.2 六个关键概念

| 概念 | 含义 | 判断问题 |
| --- | --- | --- |
| **Destination（目的地）** | 这张地图完成时应交付的状态，可以是规格、关键决定，也可以是明确允许的其他结果 | “地图走完后，什么算完成？” |
| **Map（地图）** | Issue Tracker 中的父 Issue；提供全局低分辨率视图，并链接各张子票 | “新会话先读什么，才能知道全局在哪里？” |
| **Decision ticket（决策票）** | 一个独立会话可以解决的精确问题；答案是决定或用于决定的证据，不是默认意义上的实现切片 | “这个问题现在是否已经能准确说出来？” |
| **Fog of war（战争迷雾）** | 能感觉到相关、但受前置未知影响，当前还无法准确写成问题的区域 | “我现在连要问什么都还说不准吗？” |
| **Frontier（前沿）** | 当前已知、未关闭、未阻塞、未被领取的票；也就是此刻真正可以推进的边缘 | “现在做哪件事能安全地让地图前进？” |
| **Blocking relationship（阻塞关系）** | 某项研究或决定必须先完成，后续问题才可判断或被精确表述 | “这张票的答案依赖哪张票？” |

视频用“地图前沿”和“迷雾”描述这套动态关系；作者在发布日前的官方 Skill 快照中进一步给出一个实用判据：**能否在现在精确表述问题**，而不是现在能否回答它。问题已经清楚但尚不能处理，可以建票并标记阻塞；问题本身仍含糊，则继续留在迷雾中。[03:34](https://www.youtube.com/watch?v=F3lL98Pj90o&t=214s) [发布日前官方 Skill 快照](https://github.com/mattpocock/skills/blob/260225724133c4a204489599f04642aa089259a0/skills/engineering/wayfinder/SKILL.md#fog-of-war)

### 2.3 地图是索引，不是第二份事实副本

视频展示的地图保留每项已完成工作的简要结论，细节则留在对应子 Issue。这样，新会话可以先读父地图快速定位；若某个决定与当前问题有关，再打开原始决策票查看讨论、原型或研究证据。作者称，这比只保留一份会议摘要式规格更好，因为 Agent 遇到歧义时仍能沿链接回到当时做决定的“primary source”。[04:30](https://www.youtube.com/watch?v=F3lL98Pj90o&t=270s) [10:54](https://www.youtube.com/watch?v=F3lL98Pj90o&t=654s)

发布日前的 Skill 源码把这条原则写得更明确：地图是 index，不是 store；每个决定只在它自己的票中保存完整版本，地图只写一行摘要并链接过去。这里的“primary source”指**团队决策的一手记录**，并不意味着票中引用的外部技术事实天然可靠；研究类结论仍要回到官方文档、源码或真实数据核验。

## 3. Wayfinder 如何在 Issue Tracker 中保存跨会话状态

### 3.1 父地图与子票

Pocock 在自己的 Course Video Manager 公共仓库中展示了多张 Wayfinder 地图。其中一张父地图下面有 12 个 sub-issues；每个子 Issue 对应一项决定。视频打开了一张名为“Close the clips during publish race”的已关闭子票：讨论得到结论后，详细 resolution 留在票中，父地图只同步一条缩略结论。[04:30](https://www.youtube.com/watch?v=F3lL98Pj90o&t=270s)

因此，一个最小地图可以抽象为：

```markdown
## Destination

<地图完成时要到达的状态>

## Notes

<领域背景、约束、每次会话都要读取的说明>

## Decisions so far

- [已关闭决策票](链接) — 一句话结论

## Not yet specified

<仍在迷雾中、暂时不能精确建票的问题区域>

## Out of scope

<本次目的地明确排除的内容>
```

上面模板来自视频发布日前的作者官方 Skill，而不是视频画面逐字抄录。它说明地图的持久状态至少要区分：已经决定、尚未能明确、明确不做。若只维护一个普通待办列表，这三种状态很容易混在一起。

### 3.2 Issue Tracker 不绑定 GitHub

演示使用 GitHub Issues，但 Pocock 明确说 Wayfinder 的 Skill 设计成与 Issue Tracker 无关，可以通过 `/setup-matt-pocock-skills` 配置到其他 Tracker。视频口头列举了 Linear 和 Jira；发布日前源码也定义了无外部 Tracker 时的 local-Markdown fallback。这里应理解为**流程模型可迁移**，不代表所有 Tracker 都原生支持同样完整的父子 Issue、阻塞关系、标签和并发领取体验。[05:19](https://www.youtube.com/watch?v=F3lL98Pj90o&t=319s)

## 4. 从一条模糊需求开始：命令面板案例

Pocock 用 Course Video Manager 的一次真实规划演示如何建图。他想在应用的图表窗口中加入一个 `Cmd+K` 命令面板，需求同时包含图标选择、搜索其他图表、从图表复制并保存内容等能力，范围明显超过一个小功能。地图的目的地被定为一份 **buildable spec**，即足以交给后续实现流程的规格。[05:39](https://www.youtube.com/watch?v=F3lL98Pj90o&t=339s)

初始会话大致做了这些事：

1. 用户调用 `/wayfinder` 并描述想要的能力。
2. Agent 探索仓库，了解当前系统和已有边界。
3. Agent 调用 grilling，先问“done looks like what”，并建议把目的地设为规格。
4. 经过一轮初始问题后，创建父地图和第一批子票。
5. 初始共创建 7 张票，但只有 3 张处于当时可领取的前沿，其余被依赖关系阻塞。

视频可辨认的前沿问题包括图标名称来源、组件存储 schema，以及命令面板的信息架构与键盘/网格交互。最后一项标题在自动字幕中识别不完整，本文不据此还原精确 Issue 名称。[06:01](https://www.youtube.com/watch?v=F3lL98Pj90o&t=361s)

之后，每张票都在新会话中处理。最朴素的调用方式是：

```text
/wayfinder <ticket-url>
```

Pocock 自己还用 `/handoff` 自动生成接力提示并启动 Claude sub-agent，但他强调，这只是更花哨的调度方式；Wayfinder 的核心用法仍是“第一次调用负责画地图，后续调用带着地图或具体票继续走”。Skill 本身不要求特定 Coding Agent。[06:53](https://www.youtube.com/watch?v=F3lL98Pj90o&t=413s) [07:24](https://www.youtube.com/watch?v=F3lL98Pj90o&t=444s)

## 5. 四类决策票：用不同手段降低不同不确定性

Wayfinder 不是把所有未知都交给同一种“分析”提示，而是给票标注类型，让新会话知道应该采用哪种反馈机制。

| 类型 | 适合解决的问题 | 视频中的处理方式 | 人类参与 |
| --- | --- | --- | --- |
| **Research** | 缺少外部事实、文档、API 信息或本地知识材料 | Agent 调研并带回结论；通常创建地图后就可由 sub-agent 在后台启动 | 通常 AFK，结论仍需可追溯来源 |
| **Prototype** | 仅靠语言难以判断“应该长什么样、如何工作” | 创建便宜、可丢弃的具体产物，用高保真反馈修正规划 | HITL，需要人类对产物做反应和选择 |
| **Grilling** | 业务意图、范围、取舍或实现边界还未对齐 | 围绕单一主题继续访谈与讨论 | HITL，人类不能由 Agent 代答 |
| **Task** | 某项现实动作或准备工作不完成，就无法继续做决定 | 配置、开通、联系他人、现场事务等；Agent 能做则做，不能做则交给人 | 可 AFK，也可 HITL |

### 5.1 Research：把等待事实的节点交给后台调查

研究票用来获取某个后续决定所依赖的信息。视频称，Wayfinder 通常会在建图后立即启动这类 sub-agent，因此人类不需要盯着研究过程；结果回来后写入票中，解除下游决定的阻塞。[07:49](https://www.youtube.com/watch?v=F3lL98Pj90o&t=469s)

关键不是“让 Agent 多搜一点”，而是明确研究服务于哪张后续票、需要带回什么证据。没有这个约束，调研很容易变成与目的地无关的信息堆积。

### 5.2 Prototype：防止规划退化成低保真瀑布

面对“这么多前置规划是否就是 waterfall”的质疑，Pocock 的回答是原型。大量纯文字的前置规划属于低保真推演；一个可交互或可观察的粗糙原型，则能用更高保真的反馈告诉团队实际在构建什么。Wayfinder 会在合适节点鼓励创建多个原型，并复用作者的 `/prototype` Skill。[08:02](https://www.youtube.com/watch?v=F3lL98Pj90o&t=482s)

原型的职责是提高讨论质量，不是悄悄变成生产实现。发布日前官方 Skill 将其描述为 cheap、rough、concrete artifact，并要求把产物链接到决策票；它可以是大纲、粗稿、stub，也可以是用来验证 UI 或逻辑的代码。

### 5.3 Grilling：把只能由人决定的分支留给人

追问票处理某个局部决策，例如产品行为、范围或实现边界。它不是让 Agent 自问自答一份 FAQ，而是一个真实的人机对话：Agent 逐个暴露分支，人类提供偏好、业务背景和责任判断。[08:43](https://www.youtube.com/watch?v=F3lL98Pj90o&t=523s)

### 5.4 Task：先清掉阻碍决定的现实工作

任务票用于“没有新的讨论可做，但必须先完成某件事”的情况。视频举例包括配置工作、联系某个人、外出办事；花园办公室案例中还包括委托 site survey、寻找联系人和调查承建公司。官方 Skill 对边界的表述更严格：Task 的价值是**解除一项决定的阻塞**，而不是提前交付最终目的地。[04:00](https://www.youtube.com/watch?v=F3lL98Pj90o&t=240s) [12:17](https://www.youtube.com/watch?v=F3lL98Pj90o&t=737s)

## 6. 阻塞关系与动态前沿：地图为何不是普通 Backlog

大型计划中的决定具有因果顺序。某张票即使已经能够准确描述，也可能必须等待前置研究或原型完成；Wayfinder 用 Issue Tracker 的 blocking relationship 表达这种依赖。没有阻塞、尚未被领取的开放票构成当前前沿，因此多个 Agent 只应并行领取真正独立的工作。[09:07](https://www.youtube.com/watch?v=F3lL98Pj90o&t=547s)

视频展示的另一张地图已完成 17 张票中的 14 张，但地图围绕的核心 Skill 还没构建；而等这个 Skill 有了实际形态后，又需要回头重审部分决定。这个例子说明：

- “完成票数很多”不等于路线已经确定；
- 某个关键节点会阻塞多个下游决定；
- 一张票关闭后，不只是少一个待办，还可能让迷雾中的问题变得可描述，生成新票；
- 新证据也可能使旧票失效、改变依赖，或要求重新检查先前结论。

所以，每次解决票后的核心问题不是“下一条线性任务是什么”，而是“前沿移动到哪里了”。[09:18](https://www.youtube.com/watch?v=F3lL98Pj90o&t=558s)

发布日前源码还增加了一个并发保护动作：会话开始工作前先通过 assignee **claim** 票；开放、未阻塞、未被领取的子票才属于前沿。这并不能消除所有并发写入风险，但至少避免多个会话在不知情时处理同一个问题。

## 7. 地图走完之后：从决策网络压缩为规格与实现票

当迷雾清除、目的地所需决定已经完成时，地图往往过于密集，不适合作为执行者每天阅读的实现规格。Pocock 会调用 `/to-spec`，把分散在地图和决策票中的结论压缩成一份 buildable spec。视频中的初稿甚至超过 GitHub 单个 Issue 的字符限制；这是该案例规模的信号，不是规格越长越好的目标。[09:44](https://www.youtube.com/watch?v=F3lL98Pj90o&t=584s)

再之后，他沿用自己的标准流程：

```text
Wayfinder map
  → /to-spec
  → /to-tickets
  → 逐张 implementation ticket 构建
  → code review
```

在这条链路里，Wayfinder 替代的是较小工作中的 `/grill-with-docs`：

```text
路径较清楚：/grill-with-docs → /to-spec → /to-tickets → 实现
路径有浓雾：/wayfinder       → /to-spec → /to-tickets → 实现
```

Wayfinder 规格中的决定还会链接回原决策票。如果执行 Agent 对一条摘要产生疑问，可以回看当时的完整讨论或证据，而不必把规格当成唯一、无损的事实来源。[10:25](https://www.youtube.com/watch?v=F3lL98Pj90o&t=625s) [10:54](https://www.youtube.com/watch?v=F3lL98Pj90o&t=654s)

### 决策票与实现票不能混用

| 阶段 | 票要回答什么 | 完成信号 |
| --- | --- | --- |
| Wayfinder 决策票 | “在抵达目的地前，我们还必须知道或决定什么？” | 形成可追溯决定、证据或阻塞已解除 |
| 规格后的实现票 | “已经理解的方案要如何被垂直切片并构建？” | 行为实现并通过约定验证 |

Pocock 还说明，他个人不会把规格维护成永久同步的第二份系统真相。实现完成、规格已经体现在代码后，他会关闭承载规格的 Issue，之后很少再回看；这不等于删除历史 Issue，而是停止把它当作持续更新的仓库文档。这是讲者自己的工作流选择，团队若受审计、合规或跨系统契约约束，仍可能需要持久规格。[13:14](https://www.youtube.com/watch?v=F3lL98Pj90o&t=794s)

## 8. 何时该用，何时不该用

### 适合 Wayfinder

- 工作明显超过一个高质量 Agent 会话可承载的范围；
- 知道大概想去哪里，却不知道中间路线；
- 存在多个相互依赖的产品、技术或现实决定；
- 需要在研究、原型和人类访谈之间反复切换；
- 有几条无依赖的调查线，希望多 Agent 并行；
- 需要把规划状态留在共享系统中，让不同会话或不同人接力；
- 最终产物不一定是代码，但同样具有“目的地明确、路径有迷雾”的形状。

### 不适合 Wayfinder

- 工作能在一个会话内规划和完成；
- 路线已经清楚，只差正常拆票和执行；
- 问题很小，建立父地图、标签和依赖的维护成本超过收益；
- 团队没有可共享、可追溯的状态载体，也不准备维护票的关闭、摘要和依赖；
- 实际想做的是直接实现，却把实现步骤伪装成“决策票”。

Pocock 的判断很直接：如果已经知道怎么到目的地，就在一个会话里规划；Wayfinder 专门服务“有 fog of war，只能先走一步再看见下一步”的工作。[11:38](https://www.youtube.com/watch?v=F3lL98Pj90o&t=698s)

### 非编码案例：花园办公室

讲者正在用 Wayfinder 规划自家花园里的独立办公室，包括委托现场勘测、调查需要联系的对象、寻找潜在承建公司等。这说明地图模型可以跨出软件工程；视频结尾还提到课程规划和其他工程工作。不过这些都是讲者的使用体验，没有展示花园办公室最终落地结果，也没有量化与传统项目管理方法的对照。[12:17](https://www.youtube.com/watch?v=F3lL98Pj90o&t=737s) [14:02](https://www.youtube.com/watch?v=F3lL98Pj90o&t=842s)

## 10. 可直接试点的行动清单

> 本节是整理者依据视频和发布日前官方 Skill 提炼的落地版本，不是讲者在视频中给出的固定模板。

### 第一步：先做使用门槛判断

- [ ] 这项工作是否大到一个会话无法可靠规划？
- [ ] 目的地大致可描述，但路线仍存在真实迷雾吗？
- [ ] 若路线已经清楚，是否应直接写规格或拆实现票？

### 第二步：定义目的地与范围

- [ ] 用一到两句话写清地图完成时的可观察结果；
- [ ] 明确最终要的是规格、关键决定，还是经显式授权的其他产物；
- [ ] 把明确不做的内容写进 Out of scope，不要伪装成迷雾；
- [ ] 记录领域背景、必须遵循的 Skill 和长期约束。

### 第三步：广度优先画第一版地图

- [ ] 先 across the space 暴露决策面，不要立刻钻入一个实现细节；
- [ ] 当前能准确表达的问题建成子票；
- [ ] 仍不能准确提问的区域写入 Not yet specified；
- [ ] 每张票只包含一个独立会话可以解决的问题；
- [ ] 创建完票后，再建立阻塞关系，得到真实前沿。

### 第四步：给票选择正确反馈机制

- [ ] 缺事实：Research，并要求一手来源和可复查结论；
- [ ] 缺具体感受：Prototype，先做便宜的可丢弃产物；
- [ ] 缺人类判断：Grilling，让有责任的人亲自回答；
- [ ] 缺现实前置动作：Task，说明它解除哪项决定的阻塞；
- [ ] 不要把生产实现票塞进默认的规划地图。

### 第五步：每个会话只推进一张非研究票

- [ ] 会话先读取父地图的低分辨率全局视图；
- [ ] 只领取开放、未阻塞、未被认领的前沿票；
- [ ] 先 claim，再研究或讨论，避免并发重复；
- [ ] 需要时按链接读取相关票，不要一次加载整张地图所有细节；
- [ ] 形成 resolution 后关闭票，并在父地图写一句摘要和链接。

### 第六步：每次关闭票都重新计算地图

- [ ] 哪些原本模糊的问题现在可以准确建票？
- [ ] 哪些阻塞关系已经解除？
- [ ] 新证据是否使旧票失效或超出范围？
- [ ] 前沿是否出现新的并行机会？
- [ ] 目的地所需的决定是否已经全部完成？

### 第七步：把规划交给实现流程

- [ ] 从地图和决策票压缩出 buildable spec；
- [ ] 保留规格到原决策票的链接；
- [ ] 审阅并压缩过长或重复的规格；
- [ ] 再把规格拆成实现票，不直接复用决策票；
- [ ] 实现完成后，按团队政策关闭、归档或维护规格。

## 11. 一张决策票的最小质量标准

可以用下面的模板约束试点：

```markdown
# <用问题命名的票标题>

## Question

<这次会话必须解决的一个决定或调查问题>

## Why it blocks the map

<没有这个答案，哪项后续决定无法发生>

## Type

research | prototype | grilling | task

## Depends on

<前置票链接；没有则写 none>

## Resolution

<关闭时填写：结论、证据/产物链接、仍存不确定性>
```

验收时重点看五件事：问题是否精确、是否服务目的地、类型是否匹配、阻塞关系是否真实、resolution 是否足以让后续会话继续。票写得很长、标签很多或 Agent 运行时间很久，都不是完成信号。

## 12. 常见误用

### 误用一：把所有能想到的内容一次性预切成票

Wayfinder 的地图应故意保持不完整。若当前还不能精确描述问题，就把区域放在迷雾里；强行预切只会制造虚假的确定性，后续又要大规模废弃或改写。

### 误用二：把决策票当作实现 Backlog

“决定缓存策略承诺什么”是一张决策票；“修改某文件里的缓存函数”通常已经是实现票。默认模式下，一旦开始构建最终产品，往往说明已经走到地图边缘，应把决定交给规格和实现流程。

### 误用三：让 Agent 代替人完成 HITL

Grilling 票必须由真正掌握业务或承担责任的人回答；Prototype 票也需要人类对具体产物作反应。Agent 自问自答会让流程表面闭环、实质仍在猜测。

### 误用四：让地图复制所有细节

父地图只需帮助定位。把每张票的完整讨论重新粘贴到地图，会制造两个事实副本，既增大上下文，也带来同步漂移。

### 误用五：只看完成率，不看关键路径

14 / 17 的案例说明，高完成率可能仍被一个关键节点阻塞。应看前沿、依赖和剩余迷雾，而不是把关闭票数当作主要进度。

### 误用六：把 Prototype 当成提前写生产代码

原型是为了获得高保真反馈，应便宜、可丢弃、只回答当前问题。若团队已经开始围绕原型提交大量最终代码，它就可能重新引入 Wayfinder 本想降低的沉没成本。

### 误用七：小任务也强制走完整流程

地图、标签、父子关系和回写都有维护成本。路径已知或一个会话足够时，直接规划和实现更简单，也符合讲者给出的使用边界。

## 13. 局限与注意事项

1. **视频是方法演示，不是效果实验。** 没有对照组、成功率、工期、缺陷率或 Agent 成本数据；“输出非常好”“令人解放”是 Pocock 的主观体验。
2. **案例数字不能直接成为团队默认值。** 7、12、17 张票来自不同项目和地图，不说明最佳地图规模。真正边界是一个问题能否由单个高质量会话解决。
3. **原型降低瀑布风险，但不会自动消除它。** 如果反馈人缺席、原型问题定义错误，或原型代码被直接产品化，团队仍可能在错误方向积累成本。
4. **Issue Tracker 是协作基础设施，不是正确性保证。** 标签、阻塞关系、父子 Issue 和 assignee 需要持续维护；状态过期时，Agent 只会更有条理地执行错误地图。
5. **并行有一致性成本。** Claim 可以降低重复领取，但多个会话仍可能同时修改父地图、产生冲突结论或基于过时前沿工作；视频没有给出完整的事务或冲突解决方案。
6. **“跨领域可用”仍主要是作者经验。** 花园办公室和课程规划证明讲者确实在尝试非编码用途，但视频没有展示完成质量或外部评估。
7. **非持久规格不是普遍规则。** 代码不能完整替代合规要求、业务契约、运维手册或跨团队接口文档；是否关闭后不再维护，应由项目治理决定。
8. **工具和命名会继续演化。** 本文按 2026-07-30 视频中的 `/wayfinder`、`/to-spec`、`/to-tickets` 等名称总结。作者仓库在视频之后仍会更新，不能把当前版本的新规则倒推成视频内容。
9. **字幕存在自动转写误差。** YouTube 仅提供英语自动字幕，没有人工校订轨。本文结合视频简介和作者官方源码纠正了 `/setup-matt-pocock-skills`、spec-driven development、destination 等专名；对无法可靠辨认的具体 Issue 标题没有强行还原。

## 14. 发布后官方说明补充：实践中暴露的边界

> 本节不是视频内容。它来自 2026-08-24 的作者官方说明，用于补充视频发布后汇总的现场反馈。这些是维护者记录的经验边界，不是有样本和对照组的量化研究。

| 当前官方说明记录的问题 | 对团队的实际含义 |
| --- | --- |
| Wayfinder 是整套 Skills 中最重、最密的流程 | 只有“明显超过一个会话”且“路线仍有迷雾”时才值得用；项目听起来很大不是充分条件。 |
| “默认只规划”没有硬闸门 | 官方说明把 Agent 在地图中直接写生产代码称为最常见失败。团队应人工审查 `Notes` 中的执行例外，将“build X”式 `task` 视为可能的误分类。 |
| 过早画出大而全的地图会过期 | 官方文档记录过一张 27 票地图走到第 13 张时，后续票已不再合理。应把目的地限制在一个边界清晰的 epic，并让原型证据及时淘汰旧票。 |
| 前沿允许并行，不等于并行总是安全 | 两张 grilling 票可因会话不共享上下文而重复或冲突；涉及原型选择时，方案决定权也应保留给人。官方当前把逐票推进作为更安全的默认。 |
| Tracker 能力会改变流程质量 | 没有原生子 Issue 和 blocking 的 Tracker 需从文本推断依赖，需要更多人工校正；“Tracker agnostic”不等于零成本等价。 |
| 过长、过密的问答会导致决策疲劳 | 降低 reasoning effort 或要求问题更简洁只能缓解表达成本；Wayfinder 本身仍要求人类投入真实思考和责任判断。 |
| 地图清空不等于已有实现计划 | 关闭的决策票留下的是链接化决策索引；正常仍应经过 `/to-spec → /to-tickets → /implement`，而不是直接把地图交给实现 Agent。 |

这些反馈不推翻视频的核心模型，但会改变实施口径：**把 Wayfinder 视为高成本、需人类持续把关的情境化入口，而不是所有工作的默认前置流程。**

## 15. 最值得带走的五个观点

1. **不要为了适配单次 AI 会话而缩小真正的问题。** 把规划状态外部化，让多会话共同清除不确定性。
2. **大型工作的核心产物先是决定，不是任务清单。** 路线未知时，过早拆实现票只是在编码猜测。
3. **迷雾不是失败，而是需要显式管理的状态。** 当前不能准确提问的内容不应被伪装成确定计划。
4. **不同未知需要不同反馈。** 事实用研究，行为与外观用原型，价值判断用追问，现实阻塞用任务。
5. **规划要能追溯，但不必把所有细节塞进一份文档。** 地图给全局，决策票保留一手上下文，规格为实现做压缩。

## 结语

Wayfinder 最有价值的地方，不是让 Agent 生成更多 Issue，而是换了一种对“不知道”的处理方式：不要求一次会话假装看穿全程，也不让人为了上下文限制压低项目目标；它把已知问题、尚不可问的问题、已做决定和当前可推进的边缘分开保存，再为每种不确定性选择合适的反馈机制。

当代码生成越来越快，真正容易失控的是决定如何形成、证据如何保存、不同会话如何接力，以及什么时候应该停止规划并开始构建。Wayfinder 给出的答案是一张会生长的决策地图。它不是所有工作的默认流程，但对“目的地大致可见、路线仍在浓雾里”的复杂项目，是一种值得小范围试点的工程控制方法。
